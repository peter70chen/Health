# 食物辨識、熱量與營養素準確度審查暨改善計畫

日期：2026-07-26

## 一、審查範圍

本次審查涵蓋：

- 照片與文字輸入
- Gemini 模型選擇與備援順序
- 食物辨識與份量推估提示詞
- 熱量、蛋白質、碳水、脂肪與膳食纖維估算
- AI 回傳格式、資料驗證、人工修正與儲存
- 照片保存方式與後續品質評估

本次只提出計畫，不修改功能。

## 二、目前流程

目前的照片流程是：

1. 使用者拍照或上傳一張圖片，可附加文字說明。
2. App 把原始圖片轉成 Base64，連同一段很長的提示詞送給 Gemini。
3. 同一次模型呼叫同時完成食物命名、份量估算、熱量與五項營養資料計算。
4. App 顯示單一組結果，讓使用者調整名稱、數字與食用比例。
5. 儲存前只做少量範圍與熱量換算警告。
6. 照片只作為當次畫面的暫時預覽；儲存紀錄時會移除 `blob:` 預覽網址，因此不會把每張原始照片長期塞進 App 資料。

目前模型順序：

1. `gemini-3.6-flash`
2. `gemini-3.5-flash`
3. `gemini-3.1-flash-lite`
4. `gemini-2.5-pro`

每一把 API Key 都會依序嘗試以上模型；目前沒有把「照片食物分析」和其他較簡單的 AI 任務分開選模型。

## 三、做得好的地方

- 已要求考慮台灣常見食物、便當與自助餐情境。
- 已要求混合餐盤分項思考。
- 已提醒模型把手指、餐具、盤子視為比例參考，不要當成食物。
- 已加入食用比例調整與儲存後再次修改份量。
- 已有 `confidence` 與數值異常警告。
- 已檢查蛋白質、碳水、脂肪換算熱量與總熱量是否差距過大。
- 原始照片沒有長期寫入 localStorage 或備份，避免資料體積持續膨脹。

## 四、主要問題

### 1. 一次呼叫承擔太多不同工作

同一個模型同時負責：

- 看出照片裡有哪些食物
- 猜每一項重量
- 猜烹調方式與看不見的油、醬汁
- 憑模型記憶猜每 100 克的營養值
- 算出總熱量與營養素

只要前面其中一步錯誤，後面的數字會一起偏移，而且現在無法知道錯在「辨識」、「重量」還是「營養密度」。

### 2. 只有單一答案，沒有合理區間

照片很難精確看出厚度、密度、內餡、烹調油和被遮住的部分。現行回傳只有單一重量與單一熱量，容易產生不必要的精準感。`confidence` 也是模型自行宣告，尚未經實際資料校準。

### 3. 提示詞存在容易造成錨定的規則

- 「先假設完整一份，再依比例折扣」可能讓模型先被常見份量的熱量錨定。
- 「拳頭約 250-300 ml」不適用於密度差異很大的食物。
- 手指寬度存在個人差異，也會受相機透視、距離與廣角鏡頭影響。
- 同時要求「不要低估」和「不確定時保守估計」，可能讓模型無法判斷應往哪個方向修正。
- 要求在 `notes` 60 字內放入分項、份量依據、不確定性與建議，資訊空間不足。

### 4. 回傳格式只有 JSON 模式，沒有欄位結構約束

目前只設定 `responseMimeType: application/json`，沒有提供正式 JSON Schema，也沒有對模型回傳做完整的 runtime validation。這能讓格式大致像 JSON，卻不能保證：

- 必填欄位存在
- 數值非負且位於合理範圍
- 分項加總等於總數
- `confidence` 一定是合法列舉值

### 5. 圖片處理有技術缺口

- 不論原始檔是 HEIC、PNG、WebP 或 JPEG，送出時都宣告成 `image/jpeg`。
- 沒有明確控制圖片方向、尺寸、壓縮品質與 media resolution。
- 目前只支援一張照片，無法用俯視加側視補足高度與厚度。
- 沒有辨識包裝營養標示、條碼或餐廳品項名稱的專門流程。

### 6. 營養值由模型記憶直接產生

模型適合辨識與推理，但不應是營養成分的唯一資料來源。尤其台灣混合餐點、品牌食品、醬汁與烹調油差異大，若沒有資料庫或標示依據，同一張照片重跑可能得到不同數字。

### 7. 缺少可量化的準確度基準

目前沒有固定測試照片、實際秤重值、包裝標示或人工確認答案，所以無法客觀回答：

- 新 prompt 是否真的比較準
- 3.6 Flash 是否比 3.1 Pro 更適合
- 多花的費用是否換到足夠改善
- 哪一類食物最常失敗

### 8. 使用者修正沒有形成回饋資料

App 可以讓使用者改數字，但沒有另外保存：

- AI 原始答案
- 使用者最後修正答案
- 使用模型與模型版本
- prompt 版本
- 各分項不確定性

因此無法找出長期偏差，也無法建立個人常吃食物的校正。

## 五、建議的新架構

### A. 影像辨識層

模型只負責輸出「看得到的事實與必要推測」：

- 食物分項
- 烹調方式
- 可見尺寸、容器與比例參考
- 每項重量的低值、中間值、高值
- 看不見但可能影響熱量的項目，例如油、醬、內餡
- 最需要使用者回答的一到兩個問題

不要讓這一層直接把所有數字揉成一個答案。

### B. 營養資料層

依優先順序取得每 100 克營養值：

1. 包裝營養標示或品牌官方資料
2. 使用者已確認的常用食物
3. 台灣食品營養成分資料庫
4. USDA FoodData Central 等公開資料庫
5. 找不到可靠項目時，才由模型提供估算值並明確標示為推估

### C. 決定式計算層

由程式計算每個分項及總計，不讓模型自行加總：

- `份量克數 × 每 100 克營養值`
- 加入烹調油、醬汁等獨立項目
- 蛋白質、碳水、脂肪與總熱量一致性檢查
- 分項加總與總計一致性檢查
- 顯示中央估計與合理區間

### D. 互動校正層

辨識後只問最有價值的問題，例如：

- 這是半個還是一整個？
- 飯大約吃了幾成？
- 肉有沒有去皮？
- 醬汁或湯有沒有喝完？
- 這是中杯還是大杯？

問題數控制在一到兩題，避免記錄流程變複雜。

### E. 回饋與評估層

保存數字與版本資料，不保存原始照片：

- AI 原始估計
- 使用者最後確認值
- 模型、prompt 與資料庫版本
- 食物類型與信心度
- 是否經過二次模型審核

這些資料可用來找出「飯量常高估 20%」或「bagel 厚度常低估」等個人化偏差。

## 六、Prompt 改善方向

新的提示詞應：

- 要求先列出分項，不直接只回傳整餐總數。
- 分開 `observations` 與 `assumptions`，避免把猜測當成看見的事實。
- 每項回傳 `estimatedGramsLow`、`estimatedGrams`、`estimatedGramsHigh`。
- 分別提供 `identityConfidence`、`portionConfidence`、`nutritionConfidence`。
- 將油、醬汁、外皮、內餡列成獨立分項或不確定來源。
- 要求列出一到兩個最能縮小誤差的澄清問題。
- 不要求輸出隱藏的逐步思考；改要求簡短、可核對的判斷依據。
- 用正式 JSON Schema 限制欄位、型別、列舉值與合理上下限。
- 把台灣飲食先驗保留，但避免用固定份量直接覆蓋照片證據。

## 七、模型策略

### 現階段建議

先保留 `gemini-3.6-flash` 作為主要模型。Google 官方目前將它列為 2026 年 7 月推出的穩定版，支援圖片、結構化輸出、thinking，並強調多模態與空間推理；它比仍為 Preview 的 `gemini-3.1-pro-preview` 更適合作為正式環境的預設值。

不建議只憑「Pro 名稱較強」就全面切換。正確做法是：

1. 建立同一批有標準答案的測試照片。
2. 比較 3.6 Flash 與 3.1 Pro Preview 的食物辨識率、重量誤差、熱量誤差、速度與成本。
3. 若 Pro 只在低信心或複雜混合餐盤有明顯優勢，採兩段式：
   - 一般照片：3.6 Flash
   - 低信心、分項衝突或使用者點選「精準分析」：3.1 Pro Preview 二次審核
4. 記錄實際使用的模型，不要在備援後仍讓系統看起來像是同一個模型。

同時應為照片分析設定較高的 media resolution，並評估 medium、high 的實測差異。Google 官方目前建議大部分影像分析使用 high，但仍應以本 App 的測試集確認成本效益。

## 八、拍照體驗改善

拍照準確度的優先順序建議：

1. 包裝食品先拍營養標示或條碼。
2. 一般餐點先拍俯視照。
3. 厚度或堆疊高度重要時，選擇性補一張約 45 度側視照。
4. 使用已知尺寸的卡片、餐具或常用盤子作比例參考。
5. 手指只作備用比例尺，因個人差異與透視誤差較大。
6. 拍攝後快速確認「吃之前／吃剩下」與食用比例。

不建議強迫每次都拍兩張；只有低信心或份量高度不明時才要求補拍。

## 九、測試與衡量方式

先建立 30-50 組小型測試集，涵蓋：

- 單一完整食物：bagel、香蕉、雞胸、地瓜
- 切開或吃剩食物：半個 bagel、剩飯、咬過的三明治
- 台灣混合餐：便當、自助餐、牛肉麵、滷肉飯
- 高不確定食物：油炸物、濃醬、湯麵、內餡食物
- 包裝食品與飲料

每組盡量保留：

- 實際重量或可接受的重量區間
- 包裝標示或可信資料庫營養值
- 人工確認的食物分項
- 俯視照，必要時加側視照

核心指標：

- 食物分項辨識正確率
- 重量 MAPE
- 熱量 MAPE
- 蛋白質、碳水、脂肪、纖維 MAE
- 真值落在模型估計區間內的比例
- 高／中／低信心是否真的對應不同錯誤率
- 平均回應時間與單次成本

## 十、實作優先順序

### 第一階段：低風險、高報酬

- 修正圖片 MIME type 與方向處理。
- 加入正式 JSON Schema 與 runtime validation。
- 改成分項、區間、不確定來源的 prompt。
- 分開記錄辨識信心、份量信心與營養信心。
- 保存模型與 prompt 版本。
- 建立第一批基準測試照片。

### 第二階段：計算可靠度

- 接入台灣食品營養成分資料與 USDA FDC 備援。
- 由程式依克數計算營養，不由模型直接給最終總和。
- 加入更嚴格的分項加總、每 100 克範圍與熱量一致性檢查。
- 顯示中央值與合理區間。

### 第三階段：拍照與二次審核

- 支援選擇性的第二張角度照片。
- 低信心時自動提出一到兩個澄清問題。
- 以測試結果決定是否加入 3.1 Pro Preview 二次審核。
- 包裝食品加入營養標示或條碼優先流程。

### 第四階段：個人化校正

- 比較 AI 原始答案與使用者修正值。
- 建立常吃食物與常用容器的個人校正。
- 定期檢查不同食物類型的系統性高估或低估。

## 十一、初步結論

這個功能目前最大的限制不是提示詞不夠長，也不是模型一定不夠大，而是「辨識、估重、資料查找與計算全部混在一次生成式回答裡」。最值得優先投資的是可拆解、可驗證、可比較的流程。

模型方面，現階段以穩定版 Gemini 3.6 Flash 作主模型是合理的；3.1 Pro Preview 應先經同一測試集驗證，再決定是否只用於低信心二次審核。沒有基準測試集之前，任何換模型都只能靠感覺判斷。
