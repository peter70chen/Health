# Health 食物辨識準確度最終改善計畫

日期：2026-07-26
狀態：供 Peter 審閱，尚未開始實作

## 一、最終決策摘要

### 模型決策

**主模型維持付費層 Gemini 3.6 Flash，不更換 API 供應商，也不全面改用 Gemini 3.1 Pro Preview。**

理由：

1. Gemini 3.6 Flash 是 2026 年 7 月推出的穩定正式版，官方定位包含多模態與空間推理，適合目前的照片食物分析。
2. Gemini 3.1 Pro 目前仍是 Preview，生命週期與費率限制較不穩定，不適合直接成為正式環境唯一主模型。
3. 現在最大的誤差來源不是模型等級，而是讓模型一次完成「辨識、估重、猜營養資料、加總」四件事。
4. 換成更大的模型仍看不到照片裡被遮住的內餡、實際吸油量、密度與重量；這些是影像本身缺少的資訊。
5. 改用 OpenAI 或 Claude API 會增加新的 API Key、帳務、程式介面與維護成本，目前沒有證據顯示它們對台灣食物份量估算一定優於 Gemini 3.6 Flash。
6. Google 官方條款說明，免費 Gemini API 配額提交的內容可能用於產品改善，並可能由人工審閱；付費服務的 prompts、圖片與 responses 不會用於改善產品。Health App 可能包含飲食照片與用藥相關備註，因此正式分析應使用綁定 Billing 的付費 Key。

### 準確度策略

把流程改成：

> Gemini 分項辨識與估重區間
> → 可信營養資料來源
> → App 決定式計算
> → 低信心時只問一到兩個問題
> → 使用者最後確認

### Pro 模型的定位

Gemini 3.1 Pro Preview 暫時只作為測試挑戰者，不直接上線。

只有在固定測試集證明它對「低信心、複雜混合餐盤」有明顯改善時，才加入「精準分析」第二次審核。一般照片仍由 3.6 Flash 處理。

### 照片保存

維持現在的政策：

- 日常飲食紀錄不保存原始照片。
- 照片只在當次分析時存在記憶體中。
- 儲存 AI 原始數字、使用者修正數字、模型版本與 prompt 版本。
- 測試用照片另外保存在 App 外，且只使用 Peter 願意保留的少量樣本。

## 二、目前問題的最終診斷

### 1. 單一回答混合四個不同任務

目前 Gemini 同時負責：

1. 看出有哪些食物。
2. 猜每項食物的重量。
3. 從模型記憶猜每 100 克營養值。
4. 算出整餐熱量與營養素。

任何一步出錯，最終數字就會整組偏移，而且 App 無法知道是哪一步錯。

### 2. 只有單一精確數字

單張照片通常無法可靠判斷：

- 食物厚度與密度
- 被遮住的部分
- 內餡
- 烹調油與醬汁
- 實際吃下去的比例

因此不應只顯示「487 kcal」這種看似精確的答案，而應顯示中央估計與合理區間，例如「約 490 kcal，合理範圍 410-580 kcal」。

### 3. Prompt 會造成錨定與雙重折扣

目前 prompt 要模型先想像完整一份，再依照片比例折扣；App 又有食用份量拉桿。如果使用者寫「只吃一半」，模型可能先乘 0.5，使用者再把拉桿設成 0.5，最後只剩原本的四分之一。

新規則必須明確：

- 模型只估「照片裡看得到的全部食物」。
- 使用者實際吃了幾成，只由 App 的食用比例處理。
- 若備註寫「只吃一半」，模型只回傳建議比例 0.5，不得先縮小食物重量。

### 4. 分項資料沒有結構化

現在雖然要求模型分析白飯、主菜、青菜，但分項結果全部塞在短短的 notes 裡，App 無法逐項驗證、修正或重新計算。

### 5. 圖片輸入處理不完整

- 所有圖片都宣告成 JPEG，即使原檔可能是 PNG、WebP 或 HEIC。
- 沒有明確處理方向、尺寸與壓縮。
- 沒有設定適合影像分析的 media resolution。
- 只有單張照片，厚度不明時沒有補拍機制。

### 6. 備援模型會靜默改變品質

目前同一個功能可能從 3.6 Flash 一路降到 Flash-Lite 或 2.5 Pro，但最後紀錄沒有保存實際使用的模型。這會讓相同照片在不同時間出現不同品質，也無法追查原因。

### 7. 沒有測試基準

沒有實際秤重、包裝標示與人工分項答案，就無法客觀比較：

- 新 prompt 是否更準
- 3.6 Flash 與 3.1 Pro 誰比較好
- high media resolution 是否值得
- 第二張照片是否真的改善份量估計

## 三、模型方案比較

| 方案 | 優點 | 缺點 | 決定 |
|---|---|---|---|
| Gemini 3.6 Flash 單模型 | 穩定版、現有 API Key 可沿用、速度與成本合理、多模態能力強 | 複雜餐盤仍可能估錯 | **採用為主模型** |
| 全面換成 Gemini 3.1 Pro Preview | 可能有較強推理能力 | Preview、較慢、較貴、免費層不可用，食物估重優勢尚未證明 | **不採用** |
| 3.6 Flash + Pro 低信心二次審核 | 可把較貴模型集中在困難照片 | 需要第二次呼叫，增加延遲與費用 | **測試後再決定** |
| 全面改用 OpenAI GPT-5 | 支援圖片分析與結構化流程 | 需新增供應商、金鑰、帳務與程式碼，未證明對台灣食物更準 | **目前不採用** |
| 全面改用 Claude Vision | 可分析圖片與多張圖片 | 官方也提醒空間推理與精確計數有限；需新增供應商與維護成本 | **目前不採用** |

### 明確建議

這一版不要換公司，也不要直接換 Pro。

先完成架構改造與測試集。若完成後混合餐熱量誤差仍不能接受，再讓 3.1 Pro、GPT-5 或 Claude 用同一批照片比賽；只有實際勝出且改善幅度足夠，才改正式模型。

## 四、模型路由調整

### 食物照片分析

1. 正式飲食照片與健康相關備註只使用綁定 Billing 的付費 Key。
2. 優先使用 `gemini-3.6-flash`。
3. 只有 3.6 Flash 暫時不可用時，才備援到穩定版 3.5 Flash。
4. 食物照片不再靜默降級到 Flash-Lite 或 2.5 Pro。
5. 免費 Key 不再接收真實飲食照片、個人健康備註或用藥資訊；只可用於不含個人資料的測試內容。
6. 每次儲存：
   - 實際模型名稱
   - prompt 版本
   - API 流程版本
   - 是否經過二次審核

### 其他簡單 AI 功能

不含個人或健康資訊的簡單資料擷取可使用較便宜模型。真實文字飲食描述、運動紀錄、健康教練與任何用藥備註仍走付費服務。食物照片與其他 AI 任務不再共用同一個固定模型路由。

### 資料隱私理由

依 Google 2026-03-23 生效的 Gemini API Additional Terms：

- Unpaid Services 的提交內容與回覆可能用於改善 Google 產品與機器學習技術。
- 人工審閱者可能閱讀、標註與處理 unpaid API 的輸入及輸出。
- Google 明確要求不要向 Unpaid Services 提交敏感、機密或個人資訊。
- Paid Services 不會把 prompts、圖片或 responses 用於產品改善；仍可能為防止濫用而在有限期間內記錄。

因此本 App 不應為了節省很小的單次費用，把真實健康資料優先送往免費 Key。

## 五、新的分析資料結構

Gemini 不再直接只回傳整餐總數，而要回傳：

### 整餐資訊

- 餐點名稱
- 照片清晰度
- 使用的比例參考物
- 可觀察事實
- 模型假設
- 建議食用比例
- 最多兩個澄清問題

### 每項食物

- 標準化名稱
- 食物類別
- 烹調方式
- 明確單位（食物為 g，飲料為 ml）
- 重量低值
- 重量中央值
- 重量高值
- 食物辨識信心
- 份量估算信心
- 建議營養資料候選
- 可能看不見的油、醬汁或內餡

### 三種信心分開

- `identityConfidence`：食物種類是否看得清楚
- `portionConfidence`：份量是否有可靠比例尺
- `nutritionConfidence`：營養資料來源是否可信

不能再只用一個 confidence 代表所有不確定性。

## 六、Prompt 重寫原則

### 保留

- 台灣常見飲食脈絡
- 混合餐盤分項
- 使用者備註優先
- 指出不確定性
- 油、醬汁、炸粉與內餡不可忽略

### 修改

- 先列食物分項，再估每項重量區間。
- 分開「照片看得到」與「模型推測」。
- 模型只估照片裡可見的全部份量。
- 食用比例由 App 處理，避免雙重折扣。
- 低信心時放寬區間，不要強迫猜單一數字。
- 最多提出兩個真正能縮小誤差的問題。
- 只提供可核對的簡短依據，不要求輸出 Chain of Thought。

### 移除

- 「先假設完整一份再折扣」
- 強制使用拳頭或手指固定尺寸
- 「不要低估」與「保守估計」這類互相衝突的方向
- 把大量分項資訊壓進 60 字 notes
- 食物文字 prompt 裡沒有對應欄位的水分死指令

### Structured Output

使用正式 JSON Schema 限制：

- 必填欄位
- 數字型別
- 非負值與合理上限
- confidence 合法列舉
- items 最少與最多數量
- 不允許多餘未知欄位

App 端再用 runtime schema 驗證；格式或數值不合法時不直接寫入紀錄。

### 現有重量單位 bug

目前 `FoodLog.amount` 同時承載食物公克與飲料毫升，食物清單卻一律顯示成 ml。第一階段要把欄位拆成明確量綱，並在 AI 結果卡直接顯示與允許修改食物克數。重量是熱量計算的核心輸入，不應只藏在資料裡。

## 七、圖片處理

### 第一階段

- 在瀏覽器記憶體中修正圖片方向。
- 轉成明確的 JPEG 或 WebP，再使用正確 MIME type。
- 控制長邊與壓縮品質，避免直接送出超大原圖。
- 對食物照片使用 high media resolution，並與預設設定做 A/B 測試。
- 分析完成後釋放圖片，不寫入 localStorage 或備份。

### 後續低信心流程

只有份量信心低時，才建議：

- 補一張約 45 度角照片
- 告訴 App 使用哪個常用碗盤
- 回答一到兩個問題

不強迫每餐拍兩張照片。

### 比例尺排序

1. 使用者文字說明
2. 已登錄尺寸的常用碗盤
3. 相對標準的餐具
4. 卡片等已知尺寸物品
5. 手指

手指仍可使用，但只當輔助資訊，不再視為可靠主比例尺。

## 八、營養資料來源

### 優先順序

1. 同一產品的包裝營養標示或餐廳官方資料
2. 使用者已確認且份量相同的常用食物
3. 台灣食品營養成分資料庫
4. USDA FoodData Central
5. 找不到可靠資料時，才使用模型估算

每一項都要保存來源：

- `label`
- `userConfirmed`
- `taiwanDatabase`
- `usda`
- `modelEstimate`

### 第一版資料庫做法

不先接大型即時 API。

先從台灣資料建立一份精選本機資料：

- Peter 常吃食物
- 台灣便當常見主食與配菜
- 常見蛋白質來源
- 常見水果、麵包、飲料
- 基本烹調油與醬汁

預計先涵蓋約 200-500 個常用品項；數量以實際日常命中率為準，不為了追求資料量一次塞入全部資料庫。

「常用食物」也必須補上基準重量或每 100 克營養值。現有常用食物只保存整份熱量與營養素，若沒有原始克數，不能安全套用到不同份量。固定品牌、固定早餐與同一家餐點可優先重用；每天內容不同的自助餐仍應重新辨識。

### 食物名稱對應

不把數百個名稱全部塞進 prompt。

流程改為：

1. Gemini 回傳標準化名稱、類別與烹調方式。
2. App 用本機別名表找出最接近的資料項目。
3. 高信心唯一命中就自動使用。
4. 有兩個以上合理候選時，只讓使用者點選一次。
5. 使用者確認後記住對應，下次自動套用。

### 包裝食品

營養標示辨識提前處理。若照片包含營養標示，直接讀取：

- 每份大小
- 每包份數
- 熱量
- 蛋白質
- 碳水
- 脂肪
- 膳食纖維

暫不做條碼功能；目前沒有足夠可靠且完整的台灣條碼營養資料來源，拍營養標示更直接。

## 九、App 計算與防錯

所有最終數字由 App 計算：

1. 每項重量 × 每 100 克營養值。
2. 加入油、醬汁與內餡的合理區間。
3. 分項低值、中間值、高值分別加總。
4. 最後再乘使用者食用比例。

檢查項目：

- 每項與總計是否一致
- 蛋白質、碳水、脂肪換算熱量是否合理
- 膳食纖維是否大於總碳水
- 每 100 克熱量是否超出物理合理範圍
- 單一食物與整餐數字是否明顯異常
- AI 回傳字串、空值、負值或超大值

警告應隨使用者修改即時重新計算，不可只在 AI 剛回傳時算一次。

## 十、使用者畫面

### 預設簡單畫面

- 食物名稱
- 中央熱量與合理區間
- 蛋白質、碳水、脂肪、纖維
- 食用比例拉桿
- 儲存按鈕

### 需要確認時

只有低信心才展開：

- 分項清單
- 最不確定的食物
- 一到兩個澄清問題
- 「使用較精準模型再分析」選項，前提是 Pro 測試通過

不要求使用者每次手動填寫每個食材重量。

## 十一、測試集與模型選擇標準

### 測試集

建立 40-60 組照片，涵蓋：

- 單一食物
- 切開或吃剩食物
- 台灣便當與自助餐
- 油炸、濃醬、湯麵與內餡食物
- 包裝食品與營養標示
- 飲料

每組盡量有：

- 實際秤重
- 人工確認分項
- 包裝標示或可信資料庫營養值
- 必要時的第二角度照片

每個模型、每張照片至少跑三次，先量出模型本身的重跑變異。

### 指標

- 食物分項辨識正確率
- 重量 MAPE
- 熱量 MAPE
- 7 天累積攝取的平均偏差（bias）
- 蛋白質、碳水、脂肪、纖維 MAE
- 真值落在估計區間的比例
- high／medium／low 信心與實際誤差是否一致
- JSON 合法率
- 平均與最慢回應時間
- 每次分析成本

單餐誤差仍需要評估，但這個 App 更應優先降低長期固定高估或低估。隨機誤差可能在多日平均中部分抵消；用油量、飯量或特定食物的系統性偏差不會自行消失。體重變化受水分與其他因素影響，只能作長期輔助觀察，不能拿短期體重反推每餐真實熱量。

### Pro 上線門檻

Gemini 3.1 Pro 只有同時達成以下條件才加入：

1. 在低信心或混合餐子集，熱量 MAPE 至少改善 5 個百分點，或相對改善 15%。
2. 改善幅度大於同一模型的重跑變異。
3. 食物辨識與份量估算都有改善，不只是文字說明變漂亮。
4. 延遲與費用仍可接受。
5. 上線時該模型仍受官方支援；若仍是 Preview，只提供選擇性二次審核。

### 跨供應商門檻

只有 Gemini 架構改造完成後仍不理想，才測試 GPT-5 或 Claude。若其他供應商沒有在同一測試集明顯勝出，就不增加第二套 API。

## 十二、分階段實作

### Phase 0：建立基準

工作：

- 建立第一批 40-60 組測試資料。
- 凍結現行 prompt、模型路由與圖片設定，先保存目前版本的測試結果。
- 建立自動評分腳本與結果報告。

驗收：

- 能重複比較 prompt、模型與圖片設定。
- 每筆結果知道實際使用模型。
- 有現行版本的辨識與熱量誤差基準。

### Phase 1：可靠的 AI 輸出

工作：

- 修正圖片方向、尺寸與 MIME。
- 加入 high media resolution A/B。
- 重寫 prompt。
- 改成 `items[]`、重量區間、觀察與假設。
- 加入 JSON Schema 與 runtime validation。
- 消除雙重食用比例。
- 拆分食物 g 與飲料 ml，修正食物清單錯標單位。
- 在 AI 結果卡顯示並允許修改估算克數。
- 保存模型、prompt 與流程版本。
- 真實照片與健康備註改走付費 Key。
- 食物照片限制品質一致的備援模型。

驗收：

- JSON 結構成功率至少 99%。
- 同一結果可清楚追查模型與 prompt 版本。
- 分項加總與總計沒有格式性不一致。
- 使用者寫「吃一半」不會被乘兩次。
- 食物重量不再顯示成 ml。
- 真實健康資料不再送往 unpaid quota。

### Phase 2：營養資料與決定式計算

工作：

- 建立台灣常用食物精選資料。
- 加入本機名稱別名與對應。
- 常用食物保存基準重量或每 100 克資料。
- App 依重量與每 100 克資料計算。
- 顯示中央值與合理區間。
- 加入營養標示辨識流程。
- 即時重算警告。

驗收：

- 資料庫命中的食物，營養密度重跑不再變動。
- 包裝食品熱量與標示誤差低於 5%。
- 單一常見食物熱量 MAPE 目標低於 20%。
- 混合餐熱量 MAPE 目標低於 30%，且區間涵蓋率至少 80%。

### Phase 3：低信心互動與 Pro 評估

工作：

- 低信心時提出一到兩個問題。
- 加入常用碗盤尺寸。
- 選擇性補拍第二角度。
- 以測試集比較 3.6 Flash 與 3.1 Pro Preview。
- 通過門檻才加入精準二次審核。

驗收：

- 回答澄清問題後，低信心樣本的份量與熱量誤差明顯下降。
- 不增加一般高信心記錄的操作步驟。
- Pro 未通過門檻就不上線。

### Phase 4：個人化校正

工作：

- 比較 AI 原始值與使用者最後修正值。
- 找出特定食物的系統性高估或低估。
- 記住使用者確認過的食物與資料庫對應。

驗收：

- 常吃食物再次辨識時，修正次數下降。
- 不保存日常原始照片。

## 十三、不做的事情

- 不宣稱照片估算等同電子秤或醫療級營養分析。
- 不因為 Pro 名稱較強就全面切換。
- 不把所有食物資料塞進 prompt。
- 不讓模型自行產生最終總和後直接信任。
- 不長期保存每餐照片。
- 不先做條碼資料庫。
- 不在沒有測試集前比較模型好壞。
- 不採用 Gemini 3.6 Flash 已棄用的 temperature、top_p、top_k 調整。

## 十四、建議採用方案

建議 Peter 核准以下方案：

> **付費層 Gemini 3.6 Flash 繼續當主模型；先完成分項、區間、資料庫與決定式計算。**
>
> **Gemini 3.1 Pro Preview 只進入 A/B 測試，不直接上線；通過低信心子集的改善門檻後，才作為選擇性「精準分析」。**
>
> **暫時不接 OpenAI 或 Claude API。完成架構改造後若誤差仍不滿意，再讓其他供應商用同一測試集挑戰。**

這個選擇的好處是：先解決真正造成誤差的流程問題，同時保留未來換模型的彈性，不會現在就增加另一套 API 與維護負擔。
